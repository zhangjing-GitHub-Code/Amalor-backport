# ONextBox native feature ports

The native back-panel routing, volume dependency graph/session/callback bridge, power-menu provider routing and clipboard region gate were adapted from the local ONextBox source (`com.mi.onextbox.lsp`). ONextBox is distributed under GNU GPL version 3; see this repository's GPL license and the original ONextBox project for source attribution.

These four native features and the predictive-back suboption default to false. ONextBox hot-reload infrastructure is not ported; enable the switches and use the page's restart action. Back-gesture changes restart both SystemUI and System launcher. UI changes are saved locally while disconnected and synchronized to the LibXposed `amalor` preferences group after connection.

The volume graph validates its 23-argument C17 constructor and shares the existing audio controller providers. Its private coroutine scope is canceled on destruction or fallback. Native back visuals use a no-op native back callback so ColorOS remains responsible for gesture commit/cancel; events are copied/recycled and failures retain OEM handling. Clipboard region override is scoped to `ClipboardListener.onPrimaryClipChanged` and does not change the region flag for other callers.

Device validation: restart SystemUI after enabling each option; verify power menu display/dismissal, left/right back gesture success and cancellation, volume changes/mute/live slider state, and copying both plain and sensitive content. Installation/build checks do not establish runtime compatibility with a different SystemUI build.

## Status-bar side margins

The horizontal padding adapter is adapted from ONextBox `StatusBarLayoutHooker.hookMargins` and `StatusBarLayoutRules.padding`. It changes the native home status-bar padding Rect by independent -10..10 dp offsets, bounded by each side's cutout safe inset. It copies the native Rect instead of accumulating View padding. Keyguard, vertical margins and icon ordering are not changed. Both offsets default to 0; editing enables the adapter. The expansion arrow only controls the editor's visibility, which is persisted locally. Settings use Amalor's existing local/remote synchronization. Restart SystemUI after changes to refresh native layout. Device validation is still required.

The home-screen page selector reuses the margins editor's `ExpandableConfigHeader` and `ExpandableConfigSurface`: the same stable pressed/expanded shape, arrow rotation, and unscaled height reveal from `ExpandableContent`. The existing saved expansion state and slider values are retained.

## Launcher app icons

Launcher 17.5.4 changes to workspace initialization, widget eligibility/binding/resources and predictive-back callbacks are documented in [the compatibility notes](LAUNCHER-17.5.4.CN.md). Both 17.3.12 and 17.5.4 contracts are covered by the current adapters.

The widgets menu is adapted from ONextBox `LauncherWidgetMenuHooker`, `LauncherWidgetMenuRules`, `LauncherWidgetSheetAdapter` and `LauncherWidgetSheetScope`. It appends the retained native WIDGETS factory without changing other menu entries. Eligibility remains restricted to installed, enabled app icons. The native factory still determines whether the package/user has widgets. Only actions created by this adapter and their panels use the scoped OplusWidgetCell binder; regular widget drawers retain native handling. Preview cleanup and failed-panel dismissal are preserved.

Notification badge drawing is adapted from ONextBox `LauncherNotificationDotColorHooker`, including normal/folder/big-folder scopes, shortcut-container return animations and the animated icon caller. Amalor derives real MCU primaryContainer/onPrimaryContainer roles from the original icon pixels instead of applying the donor's white scrim. Badge binding prewarms a weak bitmap/generation cache; a miss queues one low-priority worker job with at most 32×32 sampled pixels. Folder/return-animation scopes only identify the source until a badge is actually drawn. Light/dark role pairs and color filters are cached, and completion invalidates waiting views. Native color filters and number text colors are restored in finally blocks; number text uses its generated foreground role directly. See [launcher badge implementation and validation](LAUNCHER-BADGES-AND-RESUME.CN.md).

Both options default to false, are saved locally while disconnected, and synchronize to the `amalor` remote preference group. Open System launcher → Icons → App icons, enable the desired option and restart System launcher. Build validation does not establish device compatibility: check menu creation, widget preview/add/drag, normal widget drawer, app/folder badges, number readability, and disabling each option followed by launcher restart.

## Back gestures

The Back gestures row uses the same split navigation/switch interaction as Network type. Its configuration page labels the highlighted master switch Native style and provides only the boolean Native predictive back animation suboption (`native_back_predictive_animation`). The master (`native_back_panel`) controls both the AOSP visual routing and the AOSP haptic scheme. Disabling it restores ColorOS handling while retaining the saved predictive suboption. The configuration group now directly shares Network type's `ExpandableConfigSection`, including the title fade, list slide, height reveal and clipping boundary. English and Russian titles/descriptions follow the edited Chinese strings. No independent haptic selector, extra release pulse, or custom trigger-area setting is added.

The two-scope restart confirmation uses the title “重启 以下作用域？” in Chinese, with matching English/Russian text. Its body lists each localized application name followed by its package in parentheses on a separate line: `系统界面(com.android.systemui)` and `系统桌面(com.android.launcher)`. It reuses the existing AlertDialog through the shared optional text slot.

`BackGestureHapticsHook` adapts ONextBox's two scoped feedback paths: `SideGestureNavView.onUpdateGestureView` and `BackPanelController.updateArrowState`. A native bubble keeps its own threshold feedback; an OEM fallback uses the selected AOSP scheme. A retired native panel follows the ColorOS scheme when the master is off. The `View.performHapticFeedback(int)` hook is restricted to the exact panel view inside the state-update scope. System haptic settings, failure fallback, per-gesture snapshots and recursion cleanup are preserved.

26.11.35 aligns the haptic/session path with ONextBox `BackGestureHooker` and `BackGestureRules.haptics`: capture the configured scheme at a valid finger DOWN, retain it in the gesture frame, pass through untracked events, and restore the previous frame in finally. An untracked/synthetic event no longer forces the scheme to ColorOS. Native style selects AOSP (0); master-off selects ColorOS (1), including OEM visual fallbacks. Native AOSP activation/deactivation requests pass through; only the opposite scheme is translated inside the exact donor scopes. Per-method deoptimization failures are isolated. The speculative `ACTIVE` → `CANCELLED` pulse introduced in 26.11.34 has been removed. The user confirmed ONextBox was tested with AOSP scheme only, so the donor's separate enhanced-release option is not enabled.

The diagnostic build on PLQ110 observed `GONE` → `ENTRY` → `ACTIVE` → `INACTIVE` → `GONE` and an existing request for constant 24. The final donor-aligned revision still needs physical haptic confirmation: the device locked before that comparison, and the user requested delivery of the package first. Configuration/source checks must not be reported as a successful vibration test.

`BackGesturePredictionHook` and `BackGesturePredictionRoutes` preserve ONextBox's cross-activity/cross-task routing, geometry, progress, cancellation, commit animation and completion. Predictive installation now has its own retry marker and persistent hook owner instead of being a caught sub-step of bubble installation. Like the donor, each deoptimization attempt is isolated so a failed attempt cannot abort later callback/runner registration. Runner selection checks both switches, side edges, cancellation and preparation exceptions. C17's default `prepareNextAnimation` returns false for "no custom animation"; that return value must not reject the default runner. The registry constructor also retains native defaults before vendor registrations can clear them, covering an inlined registration call that would bypass the normal registration hook. `BackGestureRouteSlot` restores only the runner this port replaced, leaving external registration/removal intact.

`LauncherHomePredictionHook` preserves ONextBox `LauncherHomePredictionHooker`'s complete preview flow and per-gesture state. The begin/progress callback is resolved from the donor's method/owner-field contract, without pinning a desktop release, a `T` field, or obfuscated animator/callback class names. The port updates the same native rectangles, crop, radius and progress for the 0.85-scale AOSP home preview; native progress animation, cancellation, completion and icon handoff remain in charge.

26.11.38 corrects the 26.11.37 fixed-20dp assumption. The supplied AOSP APK reads `ScreenDecorationsUtils.getWindowCornerRadius(context)` and applies the radius in surface coordinates; this source and normal scaling are now used for owned predictive windows. On ColorOS, even the ordinary one-radius `SurfaceControl.Transaction.setCornerRadius` routes through `mTransactionExt.isSmoothRadiusOn()` to the vendor smooth setter. `StandardSurfaceCorners` makes only the active transaction's extension return false while submitting the standard radius. The preview scope routes both ordinary and Ext setters through that path before any vendor curve is queued, covering launcher light-animation overrides as well. Nested/exceptional writes restore scope in finally; unrelated transactions retain native policy. JVM checks cover identity isolation, nesting and failure cleanup. No device was connected for the final visual comparison.

26.11.40 fixes the quick-entry handoff. On PLQ110 / SystemUI 17.99.02, starting a held back gesture 180ms after opening Settings → Screen color mode reproduced an Activity/buffer layer with vendor weight 1.7 underneath a predictive leash whose weight was already 2. Waiting two seconds first produced weight 2 throughout. `ShellContinuousTransitionController.adjustBackAnimChangeLeashStateIfNeed` and `adjustFinishChangeInfoForBackAnim` copy the interrupted entry state onto both the original Activity layer and the predictive leash. These two back-only helpers now use scoped standard writes while retaining their supplied radii (including zero), matrices, alpha and reparenting.

Merely bypassing `isSmoothRadiusOn()` was insufficient for an already-used layer: the normal setter updates `CornerRadius(...)` but leaves the separate OEM weight/type fields intact. Each owned standard write now first resets those retained fields to the compositor's circular defaults (`weight=2`, `type=0`) through the Ext writer, then submits the standard radius in the same transaction. The temporary Ext policy and standard-write policy are both identity/thread scoped and unwind in finally. `BackGestureRulesCheck` covers their precedence, isolation and reset-to-standard handoff. `tests/BackCornerSurfaceCheck.py` checks the actual visible app-buffer fields in a held-preview SurfaceFlinger dump; the pre-fix positive control reports 1.7, and the fixed quick-entry preview reports 2.0/type 0. The system-supplied radius remains unchanged (135 surface pixels on the test device).

Validation: enable/disable the master from both the list and detail page; verify the predictive choice survives a master off/on cycle. After restarting SystemUI and System launcher, check left/right gesture activation and cancellation, threshold feedback with system haptics off/on, supported cross-activity/cross-task previews, return-home preview and rapid successive gestures. `tests/BackGestureRulesCheck.java` is a standalone JVM check against compiled production classes for switch dependencies, haptic routing, runner ownership and home geometry; it does not require an Android fixture.

Runtime checkpoints are distinct: `Predictive style adapters installed; nativeStyle=..., predictive=...` records installation and settings, `AOSP predictive runner selected type=...` records runner routing, and `AOSP predictive activity/task frame applied` or `AOSP launcher predictive frame applied` records the first actual native frame submission. An installation message alone does not prove the drawing path was reached.

After `:app:compileReleaseKotlin`, set the classpath to `app/build/intermediates/built_in_kotlinc/release/compileReleaseKotlin/classes` plus the resolved Kotlin stdlib JAR, then compile/run the check with `javac -cp "$classes" -d app/build/back-gesture-check tests/BackGestureRulesCheck.java` and `java -cp "app/build/back-gesture-check;$classes" me.acardia.amalor.xposed.systemui.BackGestureRulesCheck` (Windows classpath separator shown).

## Non-data SIM in separate signal style

`DataSimSignalHook` adapts the independent-only subset of ONextBox `DataSimSignalHooker` and `DataSimSignalRules`. The Status bar → Mobile network switch uses `status_bar_hide_non_data_sim`, defaults to false, and shares the existing local/remote preference synchronization and SystemUI restart action. Its Chinese title/description are “隐藏非上网卡” / “隐藏独立样式下的非上网卡”, with `ic_hide_non_data_sim`. Material selection now lives in the connected Blur/Monet button group; the retired list row's strings and icon have been removed.

The C17 `MobileUiAdapter` and `MobileUiAdapterKairos` both pass an empty list to `StatusBarIconControllerImpl.setNewMobileIconSubIds` when stacked icons are active. Filtering this entry preserves stacked mode and selects the default data subscription only from a multi-SIM independent list; unknown/missing data IDs and single-SIM inputs preserve native icons. The native method reverses its input in place, so each call receives a new mutable ArrayList while a weak controller map retains separate source/rendered snapshots. `ACTION_DEFAULT_DATA_SUBSCRIPTION_CHANGED` refreshes only changed selections on the main thread. Stacking decisions and telephony/carrier models are not replaced.

Validation: `tests/DataSimSignalRulesCheck.java` runs against the compiled production rules and covers either data SIM, reversed slot order, disabled/invalid/missing selections, single SIM, empty stacked input and native in-place mutation. `Amalor_v26.11.6_22-release.apk` passed Release/R8, `lintVitalRelease`, all three standalone rule checks and APK v2 signature verification. The packaged Chinese/English/Russian strings, both drawable resources and the filtering/receiver registrations were checked. On-device validation should cover independent icons, switching the data SIM, stacked style and disabling the option followed by a SystemUI restart.
